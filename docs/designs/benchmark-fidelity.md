# 设计稿：合成 benchmark + 保真度验证

状态：待评审 · 2026-08-14 · 设计稿，未动代码

## 背景 / 为什么

公开 README 不能写小睦生产数据（单一私有部署，token 总量会暴露调用规模——已记录的决策）。但开源项目**需要一份可发布的证据**，否则"比 headroom 更适合角色扮演"只是一句主张。

方案：**合成**。规则生成可复现的多轮角色扮演对话，埋入可验证的事实，测两个数字——token 节省率 + 事实保留率。后者是压缩最大的风险（人设漂移）的量化。

## 语料生成器

种子化的规则生成，无 LLM 参与，保证可复现、可审计：

- 固定人设前缀（仿小睦结构：persona + 共享记忆块）
- N 轮对话：模板化台词 + 随机人名/物品/事件，用 `seeded RNG` 生成
- **埋入事实**：在动态区均匀散布 K 个可验证事实（"主角喜欢薄荷糖"、"养了只叫团子的猫"），生成器记录每个事实的**特征子串**用于验证

## 两个度量

1. **token 节省**：`cl100k_base` 估算压缩前后，报告节省率 + 前缀占比——沿用现有 `/stats` 的估算逻辑。
2. **事实保留率**（核心新增）：
   - **Tier A（零依赖）**：压缩后输出里检查特征子串是否仍出现 → 程序化、无 LLM。捕获"被整段丢弃"这类致命损失。
   - **Tier B（可选，需要 LLM）**：压缩后的 prompt 喂给模型提问"主角喜欢什么？"，看能否答对。捕获"子串还在但语境碎了"的语义损失。默认关，单测不进 CI。

两者分开报告，不合并成一个"分数"——Tier A 是下限，Tier B 是语义上限。

## 关键设计决策

1. **事实必须埋在动态区**——前缀本来就不压，埋前缀里是作弊。生成器保证每条事实落在可压缩的轮次。
2. **特征子串要"区分度够"**——不能是"主角"这种到处出现的词。生成器用随机专名（薄荷糖、团子）保证。
3. **对比基线**：同语料跑 headroom（若可装）或"不压缩"原始输出，报告三个数字并列。至少报告原始 vs 压缩。
4. **可复现**：`--seed N` 固定，CI 里跑一组固定 seed，任何压缩策略改动导致的保留率波动都能被测试捕捉。

## 不做的事

- 不掺任何真实用户数据进语料（合成即脱敏）
- 不做"AI 评审回复质量"这类主观度量——只做可程序化的保留率
- 不改核心库行为，纯新增 benchmark 工具

## 验证

1. 跑固定 seed 语料，确认生成器可复现（两次跑输出字节一致）
2. 埋入 20 个事实，压缩后 Tier A 保留率报告出来
3. 人为让某策略丢失事实 → 测试能捕捉（保真度回归测试的自我验证）
