# 设计稿：前缀优化器（prefix optimizer）

状态：**已实现** · 2026-08-16 · 核心已落地（`src/roleplay_slim/optimizer.py` + CLI `optimize` 子命令 + 测试）

**与设计稿的一处偏离（诚实性修正）**：原稿设想 "若 hoist 第 3 条 → 81%" 的 what-if
曲线。实现时发现它误导——把 `prefix=k` 的 token 占比当作"hoist 到 k 后的命中率"，
会暗示能把 k 条**中间夹着变动消息**的前缀塞进缓存（前缀含变动内容就不再字节一致，
命中率会崩而不是涨）。改为：只报告可达的推荐边界 + 单独列出"被变动消息挡住、进不了
连续前缀"的稳定位置。`prefix_share_by_len` 作为纯事实数据保留在 JSON 里（token 占比，
不是命中率承诺）。

## 目标

回答接入方一个问题：**"我的哪些消息是跨请求稳定的？把它们挪进缓存前缀能省多少？"**

现状是：`segmenter.py` 在**单次请求**内识别前缀并保护它，但从不反过来分析——前缀占多少、还能不能更大、哪几条消息本可以进前缀。小睦的 76% 前缀是 `SYSTEM_PROMPT`+`SHARED_BLOCK` 恰好稳定，不是被诊断出来的。别的接入方更不知道。

## 输入 / 输出

输入：一批 OpenAI 格式的 `messages` 样本（或代理请求日志）。
输出：

```
每消息稳定度：
  idx  role      内容(前40字)                 出现率  逐字节一致率
  0    system    你是若叶睦…                   100%    100%
  1    system    [共享记忆块]…                 100%    100%
  2    user      今天作业好多…                  37%      —(每次都变)

建议前缀边界：前 2 条（约 76% 的 prompt）
若 hoist 第 3 条（87% 出现、一致率 100%）→ 前缀 81%，缓存命中率预计 +5pp
```

## 关键设计决策

1. **"稳定"的定义**：一条消息"稳定" = 跨请求**逐字节一致**且**出现率高**。两者分开报告——`出现率`高但内容每次变的（如时间戳问候）没有缓存价值，不能混进前缀。
2. **命中率预估**：假设前缀 token 占 prompt 的比例 ≈ 缓存命中率上限（这是小睦生产实测验证过的近似：76% 前缀 → 75.77% 命中）。报告"hoist 前后"两个数字，明确标注是**预估**。
3. **与 segmenter 的关系**：segmenter 消费 1 个请求，optimizer 消费 N 个。底层复用 segmenter 的消息切分与 token 估算，不重写。
4. **CLI 形态**：`roleplay-slim optimize --samples request.log --format json`，读日志文件或 stdin 喂样本。接入代理返回 JSON。
