# 设计稿：语义缓存（semantic cache）

状态：待评审 · 2026-08-20 · 设计稿，未动代码

## 先说结论

ROADMAP 里原来的描述含糊，实际上是两个完全不同的功能，价值和风险天差地别。写这份稿子的过程中判断：**其中一个方向对这个项目的核心卖点是有害的，不该做；另一个方向价值存疑，值得先质疑再决定要不要做**。这份设计稿的主要产出是把这个混淆拆开，而不是无脑照抄 ROADMAP 那句话去实现。

## 拆开两种"缓存"

### 方向 A：缓存 `compress()` 的输出（省 CPU，不省钱）

对完全相同（或近似）的动态区输入，跳过重新跑一遍 `whitespace_normalize`/`history_window`/`dedupe_verbatim_tail`/`strip_stage_directions`，直接返回上次算好的压缩结果。

- **省的是什么**：`compress()` 内部的字符串/正则运算，量级是微秒到低毫秒
- **对代理部署（这个项目的主要形态）价值趋近于零**——一次请求真正的耗时和成本大头是网络 I/O + 上游 LLM 调用，压缩这几毫秒的 CPU 完全是噪音
- **对纯库内嵌、高 QPS 场景**（不经过代理，直接在热路径里调 `compress()`）可能有一点意义，但没有任何证据这是真实瓶颈
- 精确匹配缓存**不需要 embedding**，不破坏"零 ML 依赖"——ROADMAP 原文说这个方向"会破坏零依赖纯度"是不准确的，那个代价只出现在近似匹配（下面会讲）

### 方向 B：缓存上游 LLM 的实际回复（真省钱，但有害）

对完全相同或语义相近的完整请求（"在吗"这种高频重复问候），代理直接返回缓存过的 LLM 回复，完全不再打真实的上游请求。

- **省的是什么**：真金白银的 API 调用 + 网络往返延迟——这才是 ROADMAP 原文"companion-bot 在吗 模式"想省的钱
- **但这是有害的**：角色扮演/陪伴类 bot 的魅力恰恰在于——即使被问一模一样的问题，角色每次的反应也该有细微差异（语气、措辞、有时候心情不同）。如果"在吗"每次都吐出**逐字相同**的回复，用户很快会注意到角色在放录音，直接摧毁这个项目从第一天就在讲的"persona consistency"卖点——**一致的是人设，不是台词**，这是两回事，混为一谈会把项目自己最大的卖点反过来伤到
- 近似匹配（不只是逐字相同）才需要 embedding 做语义相似度判断，**这时候才真的破坏"零 ML 依赖"**——ROADMAP 原文那句话说的其实是这个方向，不是方向 A

## 建议

**不做方向 B（缓存 LLM 回复）**，至少不作为默认行为、不作为这个项目的功能——它跟项目自己的核心主张直接冲突。如果某个接入方确实需要这种"高频重复问题走固定答案"的能力（比如客服类场景，问 FAQ 不需要每次都不一样），那是**接入方自己在应用层做的事**（存一张问答表），不该是压缩库/代理内置的行为，做了也该在文档里明确警告"这会让角色扮演类应用的回复失去变化，谨慎在人设对话路径上使用"。

**方向 A（缓存 compress() 输出）值得先质疑再决定**：目前没有任何证据表明 compress() 的 CPU 开销是真实瓶颈——0.72% 这种量级的压缩率本身就说明大部分请求的动态区不大，运算量小。在没有性能剖析数据证明这是真问题之前，加一层缓存只是增加代码复杂度换一个不存在的收益。**建议：不做，除非有人拿着真实的 profiling 数据回来证明 compress() 本身是热路径瓶颈**。

## 如果将来真要做方向 A

留一个最小化的设计，供以后有真实需求时参考：

- 缓存键：动态区消息数组的内容哈希（`content_key()` 已有的序列化逻辑可以复用）+ 影响输出的 config 字段（`keep_recent_turns`、`history_window_mode`、`stage_direction_pattern` 等）的哈希
- 缓存值：`compress()` 的返回值
- 存储：进程内 LRU（`functools.lru_cache` 或等价物），不做持久化、不跨进程共享——这是纯 CPU 优化，重启丢失完全无所谓
- 默认关闭，`CompressorConfig` 加一个 `enable_result_cache: bool = False` 开关
- 不需要 embedding，不需要新依赖

## 不做的事

- 不做方向 B（缓存 LLM 回复）——见上面的理由
- 不做近似/语义相似度匹配（embedding-based）——只有方向 A 的精确匹配值得考虑，而精确匹配的价值本身还没被证明
- 不做跨进程/持久化缓存——如果方向 A 真的要做，纯内存 LRU 就够了

## 验证（如果决定做方向 A）

1. 先做性能剖析：在真实流量形状下测 `compress()` 单次调用耗时，证明它占总请求耗时的可观比例，再决定值不值得加缓存
2. 单测：相同输入命中缓存、config 变化后不误命中、LRU 淘汰正确
3. 不改变现有零配置行为——`enable_result_cache=False` 时输出必须与当前完全一致
