# 设计稿：/stats 滑动窗口（window=N）

状态：已实现 · 2026-08-31 · 由真实生产数据触发的需求

## 背景

`/stats` 的每个数字都是**从代理进程启动（或持久化文件第一个请求）到现在的
累计值**。对"看长期趋势"是好的，但两个真实观察暴露了它的问题：

1. **压缩率被稀释**：一次短促的"重复footer流量"（`dedupe_verbatim_tail`
   能省40%+）会被 48 条先前的低压缩请求拉低到累计 `10%` 左右——真实近期
   效果看不见。
2. **缓存命中率的下降被误读**：对话越长，动态区占比越大，命中率自然从
   80% 一路滑到 65%——这是结构性必然，不是前缀缓存失效。但累计平均让
   这个"近期到底什么样"无法跟历史分开看。

累计平均适合"这台代理总共省了多少"；回答不了"最近发生了什么变化"。

## 方案

`GET /stats?window=N`（N 为正整数）：

- **顶层字段保持原样**（纯增量）。`summary()` 默认参数 `window=None`，
  行为与过去完全一致；加了参数才多返回一个 `recent` 嵌套块：
  ```json
  { "request_count": 84, "...all-time fields...",
    "recent": { "request_count": 10, "...same fields over last N..." } }
  ```
- **窗口语义**：按 `id DESC LIMIT N` 取最近 N 条请求（插入序），不是"最近
  N 条带 usage 数据的请求"——一条没带 usage 的请求也占窗口一个坑位，
  与顶层 `request_count` 的口径一致。
- `window <= 0` 返回 400。

## 为什么不做别的

- **不做 per-request 时序/趋势图接口**：那是 `/stats` 之外的另一层产物
  （需要前端），这个窗口只解决"最近的数字是多少"这个最小问题。
- **不改默认**：任何已有消费者（包括本项目自己的测试）读到的顶层字段
  逐字节不变。`window` 纯追加。

## 验证

- 单测：窗口限定最近N条、窗口大于历史≈全量、usage 块同样受窗口约束、
  窗口内无 usage 数据返回 `null`（延续"无测量≠测到0"的契约）。
- 真机（生产流量，84条真实请求）：
  - 不带参数：`request_count:84, savings_pct:12.65%, cache_hit_pct:64.94%`
  - `?window=10`：`recent.request_count:10, cache_hit_pct:64.0%`——与最近
    这批场景C单独贡献的 `1280/(1280+720)` 分毫不差
  - `?window=1`：`cache_hit_pct:49.42%`——暴露了累计平均看不到的单条
    真实情况
  - 顶层字段在带不带 window 时逐字节一致
